# ADR 0013 — 读下一个文件与扫当前文件重叠；`-i` 的块内定位改用向量归约

日期：2026-11-08　分支：`hela`　状态：已实施

## 背景

ADR 0012 之后，"双候选单趟"已经落地，归并也不再是瓶颈。剩下的账分成两笔，互不相干：

**第一笔在扫描之前。** `tests/hela/membw` 的实测给出两个数：一次同步 `read` 是 **1.8 GB/s**，
两个并发 `pread` 是 **3.1 GB/s**。而 `scan_file` 是一次一个文件、同步读完再扫 —— 读盘时 CPU 在等，
扫描时盘在等。冷语料上这两段时间**完全没有重叠**，所以端到端有接近 1.7x 的空间。

**第二笔在扫描循环里。** `-i` 比 `-c` 慢。ADR 0012 的 `index_either` 已经把它从"两趟"降成"一趟"，
但那是**稀疏**数据上的结论。在"命中密集但不满屏"的语料上（真实文本几乎都是这种：
`tests/hela/membw` 用的语料里 `z` 平均每 36 字节出现一次），`-i` 仍然慢得多。

两笔账的共同点：都不是"算法复杂度"问题，而是"某一层的开销被更高频的路径反复支付"。

## 决定一：单个读者线程 + 有界队列，FIFO 保序

`engine/readahead.odin`：

- `READAHEAD_DEPTH :: 2` —— 队列深度 2 就够。深度 1 没有重叠，深度 ≥3 只是让磁盘队列多几个
  在途请求，而 3.1 GB/s 已经被 2 个读者吃满（4 读者 3.09、8 读者 3.10，见 ADR 之外的老数据）。
- `READAHEAD_READERS :: 2`、`PARALLEL_READ_MIN :: 4 MiB` —— 单个大文件也走读者线程，但只在
  `size >= PARALLEL_READ_MIN` 时；小文件的线程启动成本比读它还贵。
- `sync.Cond` 而不是无锁环：这里的竞争者是"一个读者 + 一个主线程"，条件变量足够，
  而且**不需要**再维护一个自己写的内存序。`Cond`/`Mutex` 零值可用（`core:sync` 没有
  `cond_init`/`cond_destroy`，这一点在写的时候找了一会儿）。

**顺序是契约的一部分。** 读者按 `files` 的原始顺序入队、主线程按同一顺序取出，所以输出与串行
逐字节相同 —— 这不是"通常如此"，而是队列就是 FIFO。任何"谁先读完谁先出"的设计都会让
`-r` 的路径顺序输出变得不可复现。

`Read_Item{path, data, skipped}` 里 `skipped` 是**独立一位**，不是靠 `data == nil` 推断：
"读到了 0 字节"（空文件）与"没读"（太大 / 读失败 / 会被 `--max-size` 跳过）是两件不同的事，
而前者必须照常交给扫描器（它会报 0 命中），后者必须走原路径（措辞与退出码不变）。
第一版就是靠 `data == nil` 判断的，测试里那个 0 字节文件当场把"没读"当成了"读到了空"。

并行分块读的 `Chunk` 有一个容易写错的地方：

```odin
Chunk :: struct { file: ^os.File, file_off: i64, buf: []u8, ok: bool }
// 读的是 c.file_off + off（文件绝对偏移），不是 off（切片内偏移）
os.read_at(c.file, c.buf[off:], c.file_off + i64(off))
```

第一版没有 `file_off`，于是每个分块都从文件开头读自己的那一段长度的字节 —— 结果长度对、
内容全错，而"长度对"让一个不检查内容的测试照样通过。这个坑是用一个 32 MiB 文件、在 5 个
跨段/边界位置植入 `ZZZ`、再比对 `--dump` 与基线发现的。

**分配器必须成对。** 预读缓冲由读者线程用**进程默认堆**分配（线程入口 `context =
runtime.default_context()`），主线程释放时必须显式传同一个分配器：
`delete(item.data, runtime.default_context().allocator)`。用主线程的 `context.allocator`
在 `odin test` 下就是拿追踪分配器去 free 堆指针 —— 4 处 "bad free"。

`readahead_destroy` 必须**早于** `walk_free`：读者线程借用了 `files` 里的字符串。

### 实测

| 场景 | 串行读 | 预读 | 倍数 |
|---|---|---|---|
| 32 × 4.5 MiB，冷（`F_NOCACHE` 写入后） | 72.1 ms | 61.5 ms | **1.17x** |
| 32 × 4.5 MiB，暖（页缓存命中） | 30.5 ms | 23.2 ms | **1.31x** |
| 单文件 256 MiB，暖 | 48.1 ms | 48.5 ms | 1.00x（无可测差异） |

第三行是个诚实的负面结论：**单文件暖数据上并行 `pread` 没有收益**。页缓存命中的读取本来就是
内存拷贝，1 个读者已经打满单核的拷贝带宽，2 个读者只是在两个核上抢同一条内存通路。
所以 `PARALLEL_READ_MIN` 存在的意义只在冷读；它的阈值（4 MiB）是"线程启动成本 amortize 掉"
的经验值，不是从带宽曲线推出来的。

`XREP_NO_READAHEAD=1` 留了一条回到串行读的路。开关只做"关"：默认已经是"开"，
一个有副作用的环境开关比一个纯开关更难推理。

## 决定二：块内定位用 `select + reduce_min`，不用标量重扫

这是三个版本的故事，值得逐版记下来，因为前两版的错误都不是"算错了"，而是"没测对地方"。

### v1（ADR 0012）：两趟

```odin
ia := bytes.index_byte(d, a)
ib := bytes.index_byte(d, b)
return min(ia, ib)
```

稀疏数据上就是两倍流量（256 MiB 实测 30.3 vs 62.5 GB/s）；密集数据上退化成 O(n²)。

### v2（ADR 0012 的修法）：一趟，但块内逐字节重扫

64 字节块 → 4 个 `u8x16` 比较 → `reduce_or` 判断"这块里有没有" → **有就从这个块的起点
逐字节扫到命中处**。稀疏数据上完全看不出来（一个块里通常一次都不命中，直接跳到下一块）。
密集数据上每次调用都要多走"块起点 → 命中处"这一段：`z` 平均每 36 字节一次，块起点到命中处
平均 18 字节，7.47M 次命中 × 18 次标量分支 ≈ 1.3 亿次。

v2 里还有一个更基础的错误：折叠快路径的条件写反了。

```odin
// 排序后 lo 一定是大写（'A'=0x41 < 'a'=0x61）
if lo >= 'a' && hi == lo - 32 { return index_folded(s, hi) }   // 恒假
if lo >= 'A' && lo <= 'Z' && hi == lo + 32 { return index_folded(s, hi) }  // 正确
```

它一次都没执行过，而基准"没有变化"被我读成了"折叠没收益"。教训很直接：
**给一条快路径做基准之前，先证明它被执行过**（这次的证据是改对之后 `-t 1 -i` 从 210 ms
掉到 180 ms）。

### v3（本 ADR）：向量归约

和 `core:bytes.index_byte` 用同一套手法 —— `select(cmp, INDICES, SENTINEL_MAX)` 把不匹配的
道置成 0xFF，`reduce_min` 给出最小的匹配道号，一次归约拿到块内偏移，不做标量重扫：

```odin
off := simd.reduce_min(simd.select(cs[j], INDICES_128, SENTINEL_MAX_128))
return i + j * 16 + int(off)
```

同时补齐了 `core` 有而 v2 没有的两件事：`l < 16` 直接走标量（向量启动开销在 16 字节以下不划算）、
以及 64 字节块之后再走**16 字节块**（相邻命中只隔几十字节时，64 字节块"看到"命中却跨过它，
尾部这一段按单向量推进才不浪费）。

### 实测（`xrep --bench` 新增的 A6 组，`-o:size`，16 MiB 数据，取 3 轮最好值）

| 分布 | 模式 | 算法 | HEAD（v1 两趟） | 现在（v3） | 倍数 |
|---|---|---|---|---|---|
| 1/36 | `z` 敏感 | `single_match` | 4729.5 MB/s | 4990.6 MB/s | 1.06 |
| 1/36 | `z` `-i` | `single_match` | 1434.5 MB/s | 4961.2 MB/s | **3.46x** |
| 1/4K | `z` 敏感 | `single_match` | 57554.0 MB/s | 58394.2 MB/s | 1.01 |
| 1/4K | `z` `-i` | `single_match` | 29684.6 MB/s | 47619.1 MB/s | **1.60x** |
| 1/1 | `z` 敏感 | `single_match` | 193.2 MB/s | 193.8 MB/s | 1.00 |
| 1/1 | `z` `-i` | `single_match` | 201.4 MB/s | 204.5 MB/s | 1.02 |
| 1/36 | `gamma` 敏感 | `memchr_match` | 4268.9 MB/s | 4429.7 MB/s | 1.04 |
| 1/36 | `gamma` `-i` | `memchr_match` | 1365.3 MB/s | 4437.1 MB/s | **3.25x** |

两点值得看：

1. **HEAD 的 1/4K `-i` 恰好是敏感路径的一半**（29684 vs 57554）。这不是巧合，是"两趟"的
   定义域：在这个分布上两趟的每一趟都要扫到结尾。
2. **1/36 才是真正难受的地方**（1.434 vs 4.729 GB/s = 3.3x），而 1/1 与 1/4K 都看不出问题。
   稀疏数据走 64 字节块、块内一次都不命中就不会重扫；全命中数据退化成逐字节比较、两种实现
   同样慢。**只有"平均每几十字节一次命中"这个中间区间会稳定地走到块内定位路径。**
   这也是为什么 A6 组要用 `onebig.bin` 的真实构造（`"alpha beta gamma delta epsilon zeta\n"`
   恰好 36 字节、含一个小写 `z`）来做 1/36：密度不是编出来的。

**这张表的第一版是错的，错法值得记。** 那两行 `gamma` 当时也调 `single_match`，而
`single_match` 按定义只看 `ctx.pattern[0]` —— 于是它数的是每个 `g`。这份数据每行恰好各有一个
`g` 和一个 `z`，所以命中数与 `z` **完全相同**（7,471,147），表里看不出任何异常，只有 MB/s
偏低得离谱。修法是按模式长度显式选算法（单字节 `single_match`、多字节 `memchr_match`，
这两个正是 `select_matcher_for` 在该长度上会选的）。**基准里"跑了个算法"和"跑对了算法"
是两件事，而错误的算法可以产出看起来合理的数字。**

端到端（256 MiB 暖文件，`-o:size`，默认线程数，取 5 次最好值）：

| 命令 | HEAD | 现在 | 倍数 |
|---|---|---|---|
| `-c Q`（0 命中） | 26.84 ms | 27.36 ms | 1.00 |
| `-i -c Q`（0 命中） | 26.86 ms | 27.32 ms | 1.00 |
| `-c z`（7,471,161 命中） | 43.69 ms | 42.54 ms | 1.03 |
| `-i -c z` | 76.78 ms | 43.73 ms | **1.76x** |
| `-i -c gamma` | 82.42 ms | 46.73 ms | **1.76x** |

`-i` 现在与 `-c` **在同一条线上**（43.73 vs 42.54，差距小于测量噪声）。

## 诚实的负面结论

1. **BNDM 建表双向置位：无收益（1.01x）。** 把 `lower_table` 的折叠从扫描循环搬到预处理
   （建表时对 `b` 与 `alt_case(b)` 都置位），语义更简单（每模式一次而不是每字节一次），
   但基准没有变化。保留是因为它更好读，不是因为它更快。
2. **`match_rest` 不在热路径上，"两候选单趟"对它没有意义。** 原本的猜想是"`-i` 的剩余开销
   在多字节路径的逐字节查表"。实测否掉了：`-i` 的额外开销与模式长度**无关**
   （`"zzz"` 79.5 ms vs `"gamma"` 80.8 ms），而两者都要走 `match_rest`。开销在首字节预筛的
   每一次调用上，不在每次命中的验证里。**所以这一条不做了** —— 做了也测不出来。
3. **单文件暖数据的并行 `pread` 无收益。** 见决定一的第三行。
4. **`-t 1` 下 `-i` 与 `-c` 的 2x 差异曾被误判为"profiler 覆盖不到的段"。** 当时的推理是
   "`workers` 段两者都是 ~9.3 ms，端到端却是 88 vs 180 ms，所以差异在 profiler 之外"。真相是
   `--stats` 报的是**内层**耗时、而那个 88/180 是 python 计时出来的**外层**耗时，两者混在一起
   比；再加上一轮测量脚本在 zsh 里 `$mode` 不做词分割（`"-c z"` 被当成一个参数传入），
   于是所有数字都是假的。改用 `subprocess` 逐参数传、并且统一用 `--stats` 的内层 ms 之后，
   差异立刻定位到块内定位。**测量方法本身需要先被测量。**

## 验收

- `./verify.sh` 全绿：静态护栏、单测（lib 19 / search 40 / engine 33 / app 61）、
  78 条命令 golden 逐字节、run2 34 条、run3（krep 对齐）56 条。
- **差分对比**：同一批 240 组（15 个模式 × 16 种输出模式，`-r` 在 xrep 仓库上）与 HEAD 二进制
  逐字节相同，退出码相同，`differences: 0`。
- `search/scan_test.odin` 新增穷举对拍：长度 0..199 × 每个位置单独命中一次，`index_either`
  与 `index_folded` 都必须给出该位置；同时每个长度都验"完全没有命中"返回 -1。穷举而不是抽样，
  因为 `select + reduce_min` 最危险的失败模式（道号偏移错一位、最后一段不足 16 字节时越界）
  在抽样里很容易刚好避开。

## 没做

**只计数时不分配命中数组。** ADR 0012 已经做到"只计数就不归并"，但每个 worker 仍然在
`make([dynamic]Match_Result)` 里追加全部命中（`-c z` 上是 747 万次 append）。要去掉它需要把
`Match_Fn` 拆成"产出条目"与"只累计计数"两个签名，或者让 matcher 接受一个 `emit` 回调。
这是一个跨 6 个算法的接口改动，而在当前语料上 `-c z`（42.54 ms）与 `-c Q`（27.36 ms）的差距
只有 15 ms —— 其中还混着输出队列与归并的一部分。等有真实语料的剖面再说，先记在这里。
