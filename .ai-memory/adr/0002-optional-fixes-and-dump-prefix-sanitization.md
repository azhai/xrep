# ADR 0002 — 可选修复项与 `--dump-prefix` 文件名清洗

- 状态：已接受（Accepted）
- 日期：2026-09-12
- 关联：ADR 0001（模块拆分与能力缝隙）、README「已知行为与限制」

## 背景

模块拆分完成后，对代码做了一轮系统性的健壮性/性能/易用性审查。审查中发现
若干问题与既有契约相交，需要逐项判断"是修还是留"。

审查同时纠正了三条**不成立的前提**（避免按错误前提动手）：

| 提议 | 实际情况 |
| --- | --- |
| 为 mmap 增加 fallback | 代码里**没有 mmap**，`read_file_data` 走 `os.read_entire_file` 整读内存 |
| 优化 `simd_single_match` 的临时数组 | **没有 SIMD 实现**；`single_match` 已是 `lower_table` 查表的单层循环 |
| `slice_drop(filtered, 2)` 会让 dump 少写 | dump 用的是完整 `filtered`，实测 `--limit 2 --dump` 仍写 4 行；受影响者**仅** pretty 汇总行 |

## 决策

### 1. 修改的行为（唯一一处"契约"变更）

**`--dump-prefix` 输出名清洗。** 原实现直接拼接 `P{完整路径}.txt`，
输入含 `./` 或子目录时（如 `./data/file.bin`）会生成 `out_./data/file.bin.txt`，
要求同名目录层级已存在，否则写入失败且**一个文件都不产出**。

现改为：把路径分隔符（`/` `\`）与 Windows 保留字符（`: * ? " < > |`）逐字节替换为
`_`，长度不变。`./data/file.bin` → `out_._data_file.bin.txt`。

未采用"加 `--dump-flat` 开关"的方案，理由是：原行为在此场景下**从不成功**，
不存在依赖它的脚本；保留一个已知无法工作的默认路径只会增加分支与文档成本。

`P` 本身不参与清洗（它由用户显式指定，允许含目录）。

### 2. 新增选项（纯增量，不影响既有调用）

| 选项 | 作用 |
| --- | --- |
| `--skip-empty` | 命中 0 条时不产出 dump 文件 |
| `--dump-append` | dump 改为追加写 |
| `--max-size N` | 读入前先探测大小，跳过超大文件 |
| `-v` / `--version` | 打印版本，即时退出（与 `--help` 同语义） |

### 3. 健壮性修复

| 项 | 原行为 | 现行为 |
| --- | --- | --- |
| `--threads 0` | 0 个 worker → **静默 0 命中** | 夹到 `1` |
| `--threads 100000` | 创建上千线程，**挂死**（实测 16s 未返回） | 夹到 `逻辑核心数 × 4` |
| dump 写入失败 | 打 stderr，**退出码仍为 0** | 退出码 `1` |
| 空文件 | 仍建线程池/arena/进度条 | 快速跳过并行路径，输出与落盘语义不变 |

夹取落在 `main`（`clamp_thread_count` + `max_threads_for_machine`），
**不放在 `parse_args`**：这样解析结果保持纯数据、可被单元测试确定断言，
不随运行机器的核心数变化。

### 4. 明确不修改的行为

`--limit` 的 `slice_drop(filtered, 2)` **保留**。理由：它是 ADR 0001 登记的
既有契约（README 已知行为 #3），且实测其影响面**仅限 pretty 汇总行**——
`--count` 与 `--dump` 都用完整结果集。既然提议所依据的"影响 dump"不成立，
就没有充分理由在本次变更中动它。改为新增单元测试把该语义**钉死**，
防止未来被误改。

### 5. 常量抽取

原散落于 `scan` / `worker` / `progress` / `bench` 的魔数
（`2 MiB` 分片、`16` 字节重叠窗口、`16 MiB` arena 容量、`200 ms` 限流、
默认/上限线程数）统一提到 `common.odin` 顶层常量，并在 `common_test.odin`
中断言其基本不变量。

## 后果

**正面**：`--dump-prefix` 在相对/嵌套路径下从"必然失败"变为"正常工作"；
两个可挂死/静默错判的线程数输入被消除；落盘失败不再被脚本误判为成功；
选项默认值（`--skip-empty`/`--dump-append` 关闭、`--max-size` 为 0）保证
既有命令行行为不变。

**负面 / 需要注意**：
- `--dump-prefix` 的输出文件名发生变化，改写依赖旧文件名的脚本即可。
- 新增了 `--max-size` 的"无声 stdout"语义：被跳过的文件不打印统计行，
  原因写 stderr 且不受 `--quiet` 抑制。这是有意的取舍。
- `main` 的退出码语义变宽（新增"落盘失败 → 1"）。

## 验证

1. **回归矩阵**：原 47 条命令的 stdout/stderr/退出码与改动前逐字节比对，
   差异**仅**出现在 5 个 help 输出文件（因为帮助文本新增了 flag 说明）。
   所有 dump 内容、退出码、其余输出**完全一致**。
2. **新行为矩阵**：27 条断言覆盖 `--version`、线程数夹取（含"未挂死"）、
   dump-prefix 清洗（含"无中间目录"）、落盘失败退出码、`--skip-empty`、
   `--dump-append`、`--max-size`、多文件汇总行、空文件路径。全部通过。
3. **单元测试**：77 个用例（新增 18 个）全部通过 + 内建自检通过。

## 踩坑记录

**Odin 的 `defer` 是块作用域**，不是函数作用域。写成：

```odin
if file_size > 0 {
    filtered = scan_region_parallel(...)
    defer delete(filtered)   // ← 在本 if 结束时立即执行
}
// 此处 filtered 已被释放；随后的 dump 读到了垃圾值
```

症状极具误导性：命中**数**正确（3），但 dump 写出的偏移是垃圾（`9 / 0 / 0`），
因为释放的是后备数组而 slice 头部的 `len` 仍在栈上。诊断要点是"流式打印正确、
只有归并后的 dump 错误"。修法：`defer` 必须写在函数体顶层。
