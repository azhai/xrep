# ADR 0012 — 只数命中时不必归并；双候选预筛只走一趟

日期：2026-11-08　分支：`hela`　状态：已实施

## 背景

ADR 0011 把归并的耗时从 281 ms 降到十几毫秒，于是"归并"不再是最贵的一段，剩下的账变成
**它到底需不需要发生**：

- `--count` / `-l` / `-L` / `--quiet` 的语义里没有"哪一条"，只有"多少条"或"有没有"。
  但当时的 `scan_region_parallel` 无论调用方要什么，都先把 32 个分片列表归并成一个
  升序数组，再由调用方 `len()` 一下丢掉。
- 归并之后还有一次"区间过滤"（`--after/--before`）：它靠二分上下界 + 原地前移，
  代价与归并结果的长度成正比。而过滤的**条数**其实不需要这个数组。

另一处是首字节预筛。`find_byte` 在大小写不敏感时要两个候选字节（`t` 与 `T`），旧实现是

```odin
ia := bytes.index_byte(d, a)
ib := bytes.index_byte(d, b)
return min(ia, ib)
```

即**两趟完整扫描**。命中稀疏（最常见）时两趟都要扫到结尾，内存流量翻倍；
命中**密集**时更糟：第二个候选往往不存在，于是每命中一次都要把剩余缓冲区扫一遍 ——
复杂度变成 O(n²)。

## 决定

1. **只要计数就不归并。** `needs_items(o)` 判定调用方是否需要逐条明细；不需要时用
   `count_in_range` 在每个分片列表上二分上下界求和（每列表 O(log n)，与命中总数无关）。
   `scan_region_parallel` 的返回契约相应从 `[]Match_Result` 改为
   `(filtered []Match_Result, count uint)`：`filtered` 在没有明细需求时是 `nil`，
   而 `count` 始终准确。
2. **双候选预筛只走一趟。** 新增 `search/scan.odin` 的 `index_either`：每轮 64 字节、
   4 个 `u8x16`，一趟里同时比两个候选。`find_byte` 单候选仍走 `core:bytes.index_byte`
   （它本来就是 SIMD 的），双候选改走 `index_either`。

`needs_items` 的判据（保守，宁可多归并）：

| 选项 | 需要明细 | 理由 |
|---|---|---|
| `--dump` / `--dump-prefix` | 是 | 落盘要偏移序列 |
| `-m/--max-count` | 是 | "前 N 条"要靠流式打印，且截断后的条数是对外口径 |
| `-l` / `-L` | 否 | 只回答"有没有" |
| `-c/--count`、`--quiet` | 否 | 只要数 |
| 传统输出 / `-n` / `-o` / `--json` | 是 | 要打印偏移与上下文 |

## 结果

测量环境：Apple M4（4P+6E），64 MiB 稠密数据（每 8 字节一个命中，8 388 670 条命中），
`-o:speed`，取多次最快一轮。

### 只数命中（`-c`）

| 阶段 | 改前 | 改后 |
|---|---|---|
| workers | 41.2 ms | 33.5 ms |
| **merge → count** | **23.1 ms** | **0.32 ms** |
| free / filter | 0.03 ms | 0.01 ms |
| 端到端 | 0.06 s | 0.04 s |

merge 段本身 **72 倍**，端到端约 33%（端到端的大头是把 64 MiB 读进内存，见下）。

### 双候选（`-i`，单字节模式）

同一份 64 MiB 稠密数据，`-i -c x`（'x' 密集、'X' 完全不存在）：

| 版本 | workers 段 |
|---|---|
| 改前（两趟） | **34.6 s**（三次：35.2 / 34.7 / 33.5） |
| 改后（单趟） | **41 ms**（三次：42.7 / 40.1 / 37.2） |

**约 840 倍**，并且这不是"常数因子优化"：旧实现在"第一个候选密集 + 第二个候选缺失"时是
O(n²)，任何 `-i` 搜索一个在文本里常见的字母都会踩到。

## 验证

- `search/scan_test.odin`（新增）：`index_either` 与朴素逐字节实现逐位置对拍 ——
  块边界（0/63/64/65/127/128）、尾部、随机混排 64 轮、两候选相同、空切片。
- `odin test` 五个包全过（lib 19 / search 38 / engine 28 / app 61）。
- `./verify.sh` 全过：`tests/run.sh` golden 矩阵、`run2.sh`、`run3.sh` 逐字节比对，
  说明**输出口径没变**（计数、`-l`、区间过滤与改前逐字符一致）。
- 手工对拍：`-c` / `-c --after --before` / `-l` 三种输出的数字与改前完全相同
  （8 388 670 / 2 375 019 / 文件名）。

## 取舍

- **不顺手做 mmap 读取**。本机实测（`hela/tests/hela/membw`）：1 GiB 文件热缓存下
  `read_entire_file` 9.6 GB/s、`mmap` 13.2 GB/s（+30%），但**冷数据下两者都被盘按住**
  （单线程裸设备 1.8 GB/s，4 个并发读者才 3.1 GB/s）。语料库扫描是冷数据场景，
  所以这里真正的杠杆是"并发读、把队列深度打上去"，不是零拷贝；
  而 mmap 会改变 `read_file_data` 的生命周期契约（映射必须活到扫描结束），
  收益与风险不成比例。留作候选。
- **不改 matcher 的返回类型**（不引入"只计数"的 matcher）。那要把 `Match_Fn` 拆成两套，
  而本轮实测显示 worker 段本身已贴着内存带宽（64 MiB / 33 ms ≈ 1.9 GB/s，被
  `read_entire_file` 的 9.6 GB/s 上限压着），省下命中数组的分配是下一个数量级的活，
  等有真实语料剖面再说。

## 下一步（按价值排序）

1. **并发读**：现在是一次一个文件、同步 `read`（队列深度 1，1.8 GB/s）。把读与扫描重叠
   （读者线程 / `io_uring` 式批量）能把冷语料的扫描提到 3 GB/s 量级 —— 这是当前最大的一块。
2. `-i` 的多字节路径：BNDM 的表是按小写归一化后建的，但 `match_rest` 仍在逐字节查表，
   值得看看能否用同样的"两候选单趟"思路压掉一半比较。
3. 只计数时连命中数组都不分配（见上"不改"的理由）。
