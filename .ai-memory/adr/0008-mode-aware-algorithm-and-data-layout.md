# ADR 0008：按「模式长度」分层算法、按「操作模式」裁剪工作

- 日期：2026-10-24
- 状态：已实施
- 关联：ADR 0004（命中结果堆分配）、ADR 0006（子目录包）、ADR 0007（数据进 lib）

## 背景

ADR 0007 之后依赖清晰了，但**性能分档与操作分档都还是"一刀切"**：

- 匹配只有两档真实现：1 字节走线性扫描，其余**全部**走朴素比较（每个对齐位置
  都比较 m 个字节）；`bndm_match` 名义上是位并行，实际委托 `naive_match`。
- 多模式 `multi_match` 对每个位置遍历整张模式表，模式数翻倍就慢一倍。
- 输出队列出队是"整体左移 + pop"，单次 O(队列长度)。
- `--count` / `-l` / `-L` / `--quiet` 明明不打印明细，却仍逐条 push+pop（带锁）。
- 打印与落盘都是"每条命中一次 write 系统调用"。

基线（`./xrep --bench`，100 MiB 合成数据）：

| 用例 | 优化前 |
| --- | --- |
| 1B / 4B / 16B | 1844 / 1286 / 1200 MB/s |
| 17B / 64B / 128B | 1190 / 1039 / 880 MB/s |
| 4B -i | 1207 MB/s |
| 多模式 2 / 4 个 | 442 / 226 MB/s |
| 端到端 1 / 8 线程 | 1292 / 7142 MB/s |
| 打印 1M 行（8 MiB 稠密） | 8.20 s |
| dump 1M 条 | 1.17 s |

## 决策

### 1. 匹配：按模式长度分层，核心是「SIMD 预筛」

Odin 的 `core:bytes.index_byte` 是 SIMD 实现（amd64+AVX2 用 256 位，其它平台
128 位，不足 16 字节退化标量），且是 `contextless`、不碰分配器 —— 直接拿来当
预筛原语，不自己写内循环。

| 长度 | 实现 | 要点 |
| --- | --- | --- |
| 1B | `single_match` | SIMD 跳到候选，命中后**就地连续消费**再跳 |
| 2..16B | `bndm_match` → `memchr_match` | 首字节 SIMD 预筛 + 倒序验证 |
| 17..4096B | `memchr_match` | 同上（长模式同样吃预筛红利） |
| >4096B | `naive_match` | 表外回退，保持"永远有兜底" |

两个容易踩的点，实现里都处理了：

- **密集数据退化**：纯 `index_byte` 循环在"每个字节都是候选"时会变成
  "每字节一次函数调用"（`a` 扫全 `a` 文件）。`single_match` 因此分两段：
  SIMD 跳跃 + 命中后的标量连续段。
- **重叠命中不能丢**：候选位置逐 1 推进（`at += 1`），所以 `"aa"` 在 `"aaa"`
  里仍是 2 条；只在 `[0, n-m]` 内搜首字节，天然不越界。
- **大小写不敏感**：预筛同时查首字节的两种写法（`alt_case`），验证阶段仍走
  `lower_table` —— 结果与原实现逐字节一致。

### 2. 多模式：首字节 256 位位图

`first_bits: [4]u64`，由**所有模式的首字节**置位；当前字节不在集合里就直接
`continue`，一次模式比较都不做。仍是 O(n × Σ|pat|) 的最坏界，但绝大多数位置
被挡在外层。不引入 Aho-Corasick（模式数通常个位数，得不偿失）。

### 3. 数据结构：输出队列改环形缓冲

`Output_Queue` 用 `head` + `count` 游标，`items` 的 `len` 表示**槽位数**而非
元素数；出队 O(1)，满时扩容一倍并把环形内容按 FIFO 顺序搬到新缓冲开头。

旧实现"整体左移 + pop"在消费者（打印）慢于生产者（SIMD 扫描）时队列会堆积，
总代价 O(n²) —— 稠密命中正是这种形态（实测 1M 条打印：8.20 s → 0.38 s 里的
大部分来自这一项）。

### 4. 按操作模式裁剪：silent 不入队

`--quiet` / `--count` / `-l` / `-L` 时明细不会被打印 → worker 直接不入队，
省掉每条命中的加锁与唤醒（稠密 `--count`：0.39 s → 0.026 s）。

**只在 `-m` 未设置时启用**：`-m` 的契约是"流式到达顺序的前 N 条"，而流式顺序
只有输出线程看得到，因此 max_count > 0 时仍走完整队列。

### 5. 输出与落盘：攒批写出（64 KiB 阈值）

- `output_thread` 用 `strings.Builder` 攒批，`maybe_flush` 达阈值才写 stdout；
  `defer` 在收敛路径兜底 flush（**必须写在函数体顶层** —— Odin 的 defer 是块作用域）。
- `dump_matches` 同样攒批，不再"每条一次 `os.write_string` + 一次 `tprintf` 分配"。
- `print_hex_bytes` / `print_context` 增加可选 `sb: ^strings.Builder = nil` 参数：
  非 nil 写缓冲，否则维持原行为（既有调用点与测试不受影响）。

### 6. 行号表：SIMD 单次遍历

`build_line_index` 原是"先数一遍、再填一遍"两次标量扫描（等于把文件读两遍）。
改为用 `index_byte` 找 `'\n'` 一次遍历完成。索引本身仍是稠密 `[]u64`
（稀疏化留待将来：收益是内存，代价是 `line_of` 要局部回扫）。

## 结果

`./xrep --bench`（同一台机器，10 逻辑核）：

| 用例 | 优化前 | 优化后 | 倍数 |
| --- | --- | --- | --- |
| 1B | 1844 | 22973 MB/s | 12.5× |
| 4B | 1286 | 34118 MB/s | 26.5× |
| 16B | 1200 | 17304 MB/s | 14.4× |
| 17B | 1190 | 17129 MB/s | 14.4× |
| 64B | 1039 | 7737 MB/s | 7.4× |
| 128B | 880 | 3709 MB/s | 4.2× |
| 4B -i | 1207 | 12430 MB/s | 10.3× |
| 多模式 2 / 4 | 442 / 226 | 1502 / 1219 MB/s | 3.4× / 5.4× |
| 端到端 1 线程 | 1292 | 64581 MB/s | 50× |
| 打印 1M 行 | 8.20 s | 0.38 s | 21× |
| dump 1M 条 | 1.17 s | 0.063 s | 18.5× |
| `--count` 1M 命中 | 0.39 s | 0.026 s | 15× |

端到端的多线程**加速比下降**是预期内：匹配不再是瓶颈，剩下的是内存带宽与
同步开销；要看绝对吞吐（1 线程 1.3 → 64.6 GB/s）。

## 验证

- 129 个用例全绿、0 leak / bad free。
- `./verify.sh` 全绿：护栏 28 项 + **78 条 golden 逐字节一致** + run2 34 + run3 56。
- dump 产物与优化前 `cmp` 一致；打印输出行数不变。
- 与契约有关的断言全部保持：重叠命中、多模式同偏移各报一条、空模式无命中、
  `-m` 取流式前 N 条、`--limit` 语义、分片重叠窗口的重复上报。

## 影响

**对外行为零变化**（golden 锁定）。改动集中在 search/matcher、lib/output_queue、
engine/worker、engine/io_utils、app/scan、app/bench。

未做（记录在案，留待将来）：
- 真正的位并行 BNDM / Aho-Corasick（当前预筛已拿到大部分收益）；
- 行号表稀疏化（内存收益，需 `line_of` 局部回扫）；
- `--count` 完全不保存命中列表（与 `--dump` / `--stats` 的契约冲突，风险大于收益）。
